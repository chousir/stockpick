### 2.3 因子定義（不新增任何定義）

F1–F4 就是 docs/32 §3 的四個定義，由 `intra_pick` 既有純函式計算（`price_features`／`eps_accel_table`+`eps_asof`／`revenue_accel_table`+`revenue_asof`），
窗長與可得期限讀 `backtest.intra_pick`；**價格用原始收盤**（與 M-Pick2／3b 同，除息未還原）。point-in-time 規則同 docs/32 §3：
EPS 取保守期限次日起可用的最新季、營收取次月 11 日起可用的最新月，該期缺 → null、**不回退舊期**；窗內缺日或價格不連續 → null、不補值。
因子只取 `data_date` 當日（trailing 窗，晚幾天補跑也不受之後的列影響——有測試）。

### 2.4 母體（供評估端引用；本檔不做評估）

- **合格成員**＝`tier ∈ {top, alt, capped}`：過 gate 者（capped＝過 gate 但被同次產業／因子簇／名額上限擋下）。等價於 docs/32 §2 的 `in_main`
  在真實池的對應（趨勢分前 2 桶已由 gate 的 `bucket` 規則保證）。「同（週, 次產業）≥ 2 檔才計」由評估端套。
- 機器 Top 5＝`tier == top`。**分析師否決／最終 pick 不在台帳**（`picks.csv` 於 make week 之後才由分析師寫）；要看實際下單池得事後 join `picks.csv`。
- `source` 含 watchlist（W39：12 檔）；`held`（持股，不排名）不屬合格成員。是否限 `candidate` 由評估預註冊決定。

### 2.5 起算與凍結規則

- **起算週**：settings `start_week: "2026-W40"`；更早週拒寫（W39 前的池在台帳設計前已產出，不回補；未設定 `start_week` 則整個指令拒寫）。
- **寫入期限**：對某一週的**任何**寫入——首次寫入或重寫——都要求 今日（UTC）≤ `data_date + rewrite_days`（7 日，含當日）；**逾期拒絕**
  （`LedgerFrozenError`，底帳不動、exit 1，訊息註明「本週不入乾淨樣本」）。基準日＝該週既有列的最早 `data_date`（已有列時），否則為新列的 `data_date`；
  無法判定基準日（既有列 `data_date` 全缺，或新列無 `data_date`）→ 視為已凍結（失敗時關閉）。
  目的：(1) 乾淨樣本外證據不得在結果可見之後被改寫；(2) **不得事後才決定要記哪幾週**（選擇偏誤）——首次寫入若無期限，`recorded_at` 雖可事後偵測，
  但寫入端應直接拒絕。期限內允許「補齊快取後重跑」修復當週；期限逐週各算各的。代價：忘了記錄的週就永遠缺（一年少幾週也只是稍降檢定力）。
  runner 在載入日線快取（約 1 分鐘）**之前**先驗期限 fail-fast，`upsert_ledger` 內再驗一次（同一個 `check_write_window`）。
  注意：長假休市（如春節約 9 日）期間 `make week` 的 `data_date` 可能距今超過 7 日而被拒寫；需要時明示調高 settings 的 `rewrite_days`（改設定＝可稽核），不要靠繞過程式。
- **輸入嚴格**：`shortlist.csv` 缺台帳所需欄、型別漂移（如數值欄出現字串）、`week` 欄與目錄名不符（檔案被複製到別週）、`data_date` 不唯一 → 一律報錯不寫，
  **不**靜默轉 null（凍結證據寧可少一週、不可悄悄變形）。既有底帳讀不出來（損毀／欄位不符）→ 報錯、不覆寫、不自動修復。
- 寫入：先寫暫存再換名，不留半套檔。schema 明帶（全 null 的數值欄不會被重讀成字串）。
- **定義釘版（收集期間零改動）**：`intra_pick.py`（`56b99816…`）、`factor_lab.py`（`41d03c70…`）、`shortlist.py`（`a9fe83e1…`）三檔 git blob id 與
  docs/34 §6 的 `pinned_blobs` 相同，本 milestone 零改動（`git diff` 為空）。收集期間若生產 shortlist 規則或這些函式必須改，須在本檔記為**斷點**
  （日期＋改了什麼），評估時斷點前後不得混算。記錄器本身（`intra_pick_ledger*.py`）的變動以 git 歷史追溯。

## 5. 發現：日線快取殘缺——既有資料層缺陷，F1／F2 覆蓋率受影響（處置：R1 已做；R2 已實作並修復，分支 `fix/stock-day-month-cache-final` 待 merge）

**現象**（2026-09-30 W39 真實池煙霧測試，輸出導向暫存目錄、未寫真實台帳）：合格成員 34 檔、`mom_6_1`／`high52_near` 覆蓋率只有 **21%**
（F3 91%、F4 94% 正常）。F1／F2 的定義要求窗內完全無缺日（F1 往回 126 列、F2 往回 250 列），日線快取在窗內多處缺日。

**成因（逐項查證）**
1. **個股月檔月中抓取、月底後被當永久快取**：`twse.py::_fetch_stock_history_twse`（及上櫃版）的命中條件是
   `cache_file.exists() and (ym != current_ym or is_fresh(...))`——過去月份只要檔案存在就視為完整。月中抓過的檔（當時是「當月」）到月底後從不重抓，
   永遠殘缺。例：`stock_day_2303_202607.parquet` 只有 7 列（2026-07-01～07-09，mtime 07-10）。
2. **全市場日檔 `daily_YYYYMMDD` 只在「跑流程那幾天」才有**：`daily_all_*` 曾每個交易日一檔（2025-05-29～**2026-06-09**，整整一年），之後只有
   `fetch-twse`／週流程當天寫入的 `daily_*`（2026-07 有 10 個、2026-08 有 9 個、2026-09 有 13 個平日沒有上市日檔，含少數非交易日）。
   當初每日累積的機制是什麼、為何 6/9 後停止，**未查證**。**更正（R1 調查，2026-09-30）**：本檔先前寫的「推測與 README §12 的 cron 中斷有關」**不成立**——
   這個環境（Debian devcontainer）從來沒有 cron：沒有 `crontab` 指令、`logs/cron_fetch.log` 不存在。該推測沒查那份日誌就寫進文件，見 playbook/90 2026-09-30 第四條。
3. 兩者疊加：缺的日子既沒有全市場日檔、個股月檔又是月中定格的殘缺版 → 窗內缺日 → F1／F2 依定義為 null。
4. 這不只影響台帳：舊研究面板自 2026-06 起列數稀疏（docs/33 §6.6-1）與 `daily_all_*` 停止累積的時點吻合，**推測**同因（未逐一驗證）；
   生產的 MA／動能也讀同一批快取（`twse.py` 個股歷史讀取合併 `stock_day_*` 與 `daily_*`）。

**我做了什麼（2026-09-30，僅新增快取檔、未改任何程式與既有檔）**
- 用專案既有的 `client.fetch_daily_all_historical`（官方 TWSE MI_INDEX，一天一請求、節流 1 秒、已快取的日子自動跳過）補 2025-09-15～2026-09-29 缺的平日：
  52 個請求 → **新增 31 個上市交易日檔（2026-06-24～2026-09-23）**、21 個為非交易日（空回應）、失敗 0。
- 同法嘗試補上櫃全市場日檔（2026-06 起 51 個 TWSE 交易日）：**全數空回應**（「無資料或端點不支援回查此日」）——上櫃全市場日線確實補不回，README §12 的說法對上櫃仍成立。
- 成效（同一份 W39 池）：F1／F2 覆蓋率 **21% → 68%**；34 檔合格成員中 **上市 23 檔全部完整、11 檔缺日全是上櫃**：其中 10 檔缺 7～13 個交易日
  （集中在 2026-06-15～07-30 與 09-29），另 7828 創新服務窗內缺 154 個——**更正（R2 調查）**：它是 **2026-04-23 才上櫃掛牌的新股**：TPEX 上櫃日線端點對它 2026-02、03
  回空、官方快取最早日期就是 2026-04-23（FinMind 較早的 233 列多半是興櫃期間；這是「用 FinMind 列數驗證官方上櫃日線」的錯誤，見 playbook/90 2026-09-30 第五條），
  故窗內天然缺日、F1／F2 為 null 屬正常。0.68 < 0.70 → 記錄器與 week-check 會警告，且點名缺值股票。
- 影響其他輸出：W40 `make week` 讀到的日線比 W39 完整，趨勢分／輪動基準等用近數月日線的計算數字可能與 W39 口徑略有差異（更完整、非更差；**未量化**）。

  `0 10 * * 1-5 /bin/bash /workspaces/stockpick/scripts/fetch_cron.sh`（容器時區 UTC：10:00 UTC＝台北 18:00；T86 法人 15:00 起穩定）。
  驗證：臨時每分鐘測試工作於 11:23:01 以 `vscode` 觸發（已移除）；`env -i PATH=/usr/bin:/bin` 模擬 cron 精簡環境跑腳本 rc=0。
- **限制（重要）**：容器內 cron **不會撐過容器重啟／重建**——PID 1 是 `sh`（無 init；實測當時容器已連續執行 7 小時 41 分）；每次容器啟動後需 `sudo service cron start`，
  容器重建後 cron 套件與 crontab 都會消失；且排程只在容器**正在執行**時才會觸發。上櫃全市場日線只能當天（最遲到下個交易日 15:00 前）抓，漏一天就永久缺——
  所以 R1 對上櫃只能減少新洞、**補不回既有的洞**（2026-06-10～09-29，含 09-29 的 `otc_daily_*` 整日缺）。
- 想持久化（**未測試的建議，需你裁決；只有重建容器才會生效**）：`.devcontainer/devcontainer.json` 加 `"postStartCommand": "sudo service cron start"`，並在
  `postCreateCommand` 尾端接 `&& sudo apt-get update -qq && sudo apt-get install -y -qq cron && (crontab -l 2>/dev/null; echo '0 10 * * 1-5 /bin/bash /workspaces/stockpick/scripts/fetch_cron.sh') | crontab -`；
  或改在主機端排 `docker exec <容器> /bin/bash /workspaces/stockpick/scripts/fetch_cron.sh`（容器仍須在跑）。
