## 0. 定位：兩個方向相反的哨兵（委託書 M8「定位澄清」）

| | M2 `market_washout` | M8 宏觀窄橋消費的美股掃描 |
|---|---|---|
| 抓什麼 | 台股內部**抓底** | 全球（美股）**抓頂** |
| 訊號語意 | 極端**負**讀數＝接近落底 → 禁止在此區追加減碼 | 過熱/槓桿/情緒極端 → 收緊新倉 |
| 資料 | 本機快取（融資／廣度／regime 資金子分／等權指數） | 人工掃描產出的 `macro_risk_latest.yaml` |
| 進 pipeline？ | ✅ 進 `make week`（純揭露，不改燈色/排序） | ❌ 檔案人工放進輸入包 |
| 影響 | 報告層語意（豁免可用、左側升必列段） | 倉位節奏（姿態降級、新倉封 ⅓） |

**兩者不可互相取代，也不可合成一個分數。** 同時出現（台股投降底 × 美股過熱頂）不是矛盾，
是「本地已洗完、外部風險未解」——照兩段各自的讀法並列給人看，由人判斷。

repo 的市場層模組因此變成五塊：`data/macro.py` 事件行事曆、`analysis/regime.py` V2 內生
regime、`analysis/macro_regime.py` 外生總經燈號、`analysis/washout.py`（本檔 M2）、
以及 M8 這座窄橋。前三塊見 docs/25／docs/26。

## 1. M2 投降洗盤偵測（`analysis/washout.py`）

### 1.1 為什麼要獨立成 flag，不能併進 regime

現行 V2 regime 是**線性加權**（趨勢/廣度/資金）。洗盤底部三分項會同時深負 → 姿態在
「最該警戒反轉」的那一刻喊出最防禦。投降偵測的語意**與加權方向相反**：極端負讀數是
「接近落底」的證據。把它加進 regime_score 只會兩個訊號互相抵銷、一起消失。

故：**獨立計算、獨立呈現，不進 regime_score、不改燈色、不改排序、不改剔除**
（比照 `contrarian_base`／`near_flow`／`trajectory` 的「揭露非 gate」pattern）。

### 1.2 四個子項（≥2 命中即觸發）

| # | 子項 | 判準 | settings |
|---|---|---|---|
| 1 | `margin_capitulation` | 全市場融資餘額**單日 / 5 日**減幅 z 取較極端者 < −2 | `washout.margin` |
| 2 | `breadth_washout` | 全宇宙站上 MA60 比率 < 20% | `washout.breadth` |
| 3 | `flow_extreme_streak` | regime 資金子分 < −0.9 且**尾端連續** ≥3 週 | `washout.flow` |
| 4 | `index_deep_deviation` | 等權指數距自身 MA60 < −7% | `washout.index` |

**分母誠實**：`n_evaluable` 只算 `status=ok` 的子項，報表印「已求值 N 項中觸發 M 項」
（沿 docs/26 §6.2(5) 的口徑，不把分母硬寫成 4）。子項算不出來 → 分母縮小、分子不變，
判定只會更難觸發，方向保守。

### 1.3 觸發後行為（委託書 M2.3・全在報告層，不自動下單）

- regime 姿態改印「**深跌後段・反轉警戒**」＋「極端讀數＝投降特徵，禁止在此區追加減碼」。
- 恐慌豁免（M3.2）進入可用狀態，持股表逐檔標「豁免適用/不適用」（週報 prompt patch-2）。
- 左側清單（M1）升級為決策卡必列段（非附錄）。
- flag 落 `data/washout/washout_history.parquet`（**同日冪等**，沿 `macro_regime.append_history`
  同一模式），供未來回測驗證偵測本身。

### 1.4 校準狀態：**未校準**（委託書「誠實帳」明列）

歷史面板只有**一次** 530 億級投降樣本（2026-07-30），這批門檻是**先驗值不是校準值**。
依委託書 M2.2 括號要求，**上線前 4 週本 flag 只描述、不判勝負**；門檻調整一律走
`config/settings.yaml` diff，不在程式裡調。渲染段固定印這條警語。

### 1.5 三個口徑降級（讀數字前必看）

**(a) 融資＝張數、僅上市。** 新聞說的「7/30 融資單日減逾 530 億」是**金額**口徑；本模組
沒有金額序列（TWSE MI_MARGN 個股表只給張數，市場加總表本 repo 未解析），z 建在**張數
代理**上。兩個口徑的數字**不可互相引用**。

**(b) 融資變化用來源欄、不自己 diff。** margin 快取**有缺日**（週跑節奏下 `fetch_margin`
一週只補一天）。對「可得日序列」做 `diff(1)` 會把跨缺口的多日變化當成單日變化，z 分母
被灌大、極值被稀釋。改用 TWSE 自己給的 `margin_chg`（該日對前一交易日）加總＝gap-proof。
5 日窗另加連續性檢核：尾端 5 列橫跨 > 9 個日曆天 → **該窗誠實棄用**，只留單日窗。

**(c) 「大盤」＝等權指數，不是加權 TAIEX。** 沿 `analysis/regime.py` 明文修正過的口徑。
等權對中小型股的投降更敏感，方向一致但幅度不可與大盤指數對表。

### 1.6 ⚠️ 實作時發現的既有缺陷：日線快取覆蓋極不平均

**實測（2026-08-08）**：`data/cache/twse/daily_*.parquet` 的每日宇宙大小差距懸殊——

| 日期 | 有報價檔數 |
|---|---|
| 2026-07-24 | 5,840 |
| 2026-07-27 ~ 07-30 | **各 10** |
| 2026-07-31 | 5,777 |
| 2026-08-03 | 199 |
| 2026-08-06 | 191 |
| 2026-08-07 | 6,342 |

等權指數在「只有 10 檔」的日子等於那 10 檔的平均，chain 下去會生出憑空的 −20% 級跌幅。

`regime.compute_breadth_score` **早就有** `min_priced` 這道閘（薄覆蓋 → 廣度回 None，
這正是 `regime_labels.parquet` 在 2026-07-29/30 兩天 `breadth_score` 為 null 的原因），
但 **`compute_market_index` 沒有**——regime 的**趨勢分項**因此一直吃著未設防的指數。

**本 milestone 的處置（刻意保守）**：
- 在 M2 範圍內自保——`dense_days()` 先濾掉覆蓋 < `min_priced` 的交易日再建指數；
  最新交易日若本身是薄日 → 子項 4 回 `insufficient_data`（不用薄樣本算乖離）。
- 濾掉的日子其個股報酬會併進次一足量日（chain 的性質），**幅度仍不精確**——子項 4 的
  detail 會自動附註「回看窗內 N/M 日被剔除 → 只讀方向」。
- **不動 `regime` 既有行為**。修 regime 的趨勢分項＝改變既有輸出，應該是獨立 milestone
  ＋自己的回歸對表，不該夾在本委託裡順手改（CLAUDE.md「不要順手改鄰近程式碼」）。
- 根治手段是把快取補密：`make backfill-daily-history START=... END=...`（MI_INDEX bulk，
  一天一請求）。**列為下一輪候選，本輪不做。**

## 2. M8 宏觀窄橋（`analysis/macro_risk.py`）

### 2.1 這是一座窄橋，不是一條管線

每日 17 指標掃描是**獨立 project**（§3／M9），走網路搜尋、產出人讀報告。本模組只讀它
吐出的一小段機器摘要 `macro_risk_latest.yaml`。**17 項指標不進 pipeline**——理由是
docs/26 §1–§3 已裁決的三條：一半不可程式化取得、頻率錯配（日掃季頻資料）、對台股目標
從未實測。

```yaml
# reports/<週次>/macro_risk_latest.yaml（人工從掃描 project 貼進輸入包）
macro_risk: {date: 2026-08-08, triggers_hit: 2, of: 7,
  hits: [HY_spread, margin_debt_mom], vix: 18.3, fng: 41}
```

### 2.2 與 docs/26 既有裁決的關係（**兩處，必須一起讀**）

**(a) `3-of-7` 的分母——不推翻，照 docs/26 §6.2(5) 落地。**
docs/26 §2 裁決「`3-of-7` 在本 repo 永遠算不出來」（七條硬觸發只有 2 條能自動求值，
把分母寫成 7 是「規則本身無法被求值」）。本模組**不推翻這條**：`of` 欄承載的是
**已求值項數 N**，不是常數 7，報表一律印「已求值 N 項中觸發 M 項」。人工掃描可用網路
搜尋補到 FRED 拿不到的那批，故 N 通常 > 2 但不會滿 7。

門檻掛法刻意不對稱，理由是誤判方向不同：

| | 判定 | 為什麼 |
|---|---|---|
| **gate 那側**（≥3 觸發） | 不設 coverage 門檻 | 未求值的項只會**少算**觸發數 → 「已觸發 ≥3」在任何 coverage 下都保守安全，不會因分母薄而誤觸發 |
| **註記那側**（0–2 觸發） | coverage < `min_coverage` 必須帶警語 | 危險的是把薄分母的「0–2」讀成「風險已清」——這才是 docs/26 §2 真正在防的事 |

**(b) 裁決 D 局部覆寫 docs/26 §6.2(4)。**
docs/26 §6.2(4) 原文是「輸出不得建議調整本專案的排序/剔除/燈色」。裁決 D 放寬了一部分：
現在**允許影響姿態與倉位節奏**（降一級、新倉封 ⅓），但**仍不影響選股**。這條界線是刻意的
——docs/26 §3.2 指出這 17 項對**台股目標**從未實測，傳導鏈（台股 beta、外資流）真實但慢
且弱，所以它可以調節「買多大」，不能決定「買哪檔」。

### 2.3 三態容錯（委託書 M8：一律降級為註記、不擋流程）

| status | 條件 | 行為 |
|---|---|---|
| `ok` | 檔在、schema 合法、日期未過期 | 依 §2.2 的 gate 影響姿態與新倉上限 |
| `missing` | 檔不在（本週沒跑掃描） | 明寫「宏觀掃描缺席，不當 gate」 |
| `stale` | 掃描日落後 > `stale_trading_days` 個平日 | 明寫「宏觀掃描過期，不當 gate」 |
| `invalid` | 檔在但 schema 壞（缺鍵/日期格式錯/`hit > of`） | 同 missing 處理，另印壞在哪——**不半信半疑地用**，非 ok 狀態下數值欄一律 None |

**新鮮度用「平日數」不扣國定假日**：本 repo 沒有美股行事曆，硬編一份會過期。誤差上限
約 1–2 天，方向已知——連假期間可能**提早**判 stale，後果是少用一個未經本系統驗證的外部
訊號，在 docs/26 §3.2 的立場下是可接受的那一邊。

### 2.4 落地位置（**沒有憑空發明 pipeline stage**）

週報是 docs/11 的**人工貼檔流程**，repo 裡**沒有**程式化的「週報輸入 loader」
（`report/builder.py` 是**個股報告**用的）。所以 M8 落成四件真實存在的東西：

1. `analysis/macro_risk.py`——純函式 loader/validator/gate（可測、三態齊全）。
2. `tw-screener market macro-risk [--week]`——人工查狀態＋拿披露 yaml 片段。
3. `week-check` 尾段多印一行三態提示（**不列進 missing_machine**——這是人工可選檔，
   缺席合法，同 `excluded.csv` 的自願制）。
4. docs/11 Step A 檔案清單 ＋ 貼檔順序 ＋ patch-6 消費規則 ＋ 披露 yaml 新鍵 `macro_risk`。
