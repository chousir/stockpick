# 40 — 維護協議（怎麼安全地更新 CLAUDE.md／playbook／memory）

> 觸發條件：想改 CLAUDE.md、playbook/ 任何檔、memory 索引，或踩坑後要記教訓。

## §1 權限分級
**綠區（自行改，改完在回報裡提一句即可）**
- playbook/90-lessons.md：append 新條目（不改舊條目）。
- playbook/10 §1 環境事實段：查證後更新（附新查證日期）。
- 修正路徑錯誤、錯字、失效連結（改前確認新路徑真的存在）。
- playbook/30 模板的填空提示微調（不動三件套結構）。
- memory：新增記憶檔＋索引行（守 §3 行長規則）。

**黃區（先問使用者，附「現行 vs 提案 vs 理由」再動）**
- CLAUDE.md 任何改動（尤其鐵律段）。
- playbook/10 §6 升降級規則、playbook/20 各 rubric 本體。
- 刪除或合併任何 playbook 檔。
- playbook/60 人設（角色定位、報告框架、禁止事項）。
- .claude/agents/*.md 的新增或修改。

**紅區（不做，使用者親自下令也要先複述風險）**
- 刪 playbook/_backup/ 下的備份。
- 改 docs/02 Goodinfo 合規規則。
- 繞過「驗證不自驗」協議（例：跳過 verifier「因為改動很小」）。

## §2 改檔程序（黃區照做，綠區可簡化）
1. 備份：`cp <檔> playbook/_backup/<檔名>.<YYYYMMDD>`（memory 檔備份到 memory/ 的上層目錄，不進 repo）。
2. 改動。
3. read-back 驗證：派 verifier 確認「檔案存在、新段落在、被引用的路徑都真實存在」。
4. 一致性檢查：改了檔名或段落編號 → grep 全 playbook/＋CLAUDE.md 的舊引用，一次改完（文件漂移是本 repo 最高頻錯，見 playbook/90）。

## §3 Memory 衛生
- 索引（MEMORY.md）一行一鉤 **≤120 字元**：主題＋狀態＋一個鉤子。想寫更多＝內容放錯位置，寫進記憶檔本體。
- 記憶檔本體不限長，但同主題更新既有檔，不開重複檔。
- 錯了的記憶直接刪（檔＋索引行一起）。
- 索引超過 30 行 → 把已收官、超過一季未碰的專案條目合併成一行「歷史收官索引」型條目（細節都在各檔裡，不會丟）。

## §4 90-lessons 精簡程序
- 觸發：超過 150 行。
- 做法：把「已制度化」（落點欄有檔名）的舊條目濃縮成一行移到檔尾「已制度化索引」段；未制度化的條目保留全文並優先處理（要嘛制度化、要嘛標明為什麼不）。
- 精簡屬黃區：先給使用者看濃縮前後對照。

## §5 行數上限（超過＝該精簡的訊號，不是硬擋）
| 檔 | 上限 | 超過時 |
|---|---|---|
| CLAUDE.md | 80 行 | 把最少用的段抽進 playbook，留路由行 |
| playbook/ 各檔 | 200 行 | 抽子檔或砍過時內容（黃區） |
| MEMORY.md | 30 行 | §3 合併程序 |

## §6 定期維護（掛在既有節奏上，不另開排程）
- 每季跑 `make pick-outcome` 校準時，順做：playbook/10 §1 環境事實重查證（模型 enum、agent types）＋90-lessons 是否觸發精簡＋MEMORY.md 行數檢查。
- 發現路由表指到不存在的檔 → 當場修（綠區），並記 90-lessons。

## §7 什麼「不要」寫進這套制度
- repo 已記錄的事（code 結構、git 歷史、docs 內容）——寫了就會漂移。
- 一次性的任務細節——那是 memory 或 lessons 的事。
- 抽象要求（「保持高品質」）——寫不出判準的規則等於沒寫，先想清楚判準再寫。
