# 20 — 判斷力 rubrics（何時升級／何時算完成／何時問人／何時換路／品質底線）

> 觸發條件：不確定「做完了嗎、卡住了嗎、該問使用者嗎、方向對嗎」的任何時刻。
> 每條判準附正例✅（該這樣）與反例❌（不該這樣）。例子多來自本 repo 真實歷史。

## §1 何時該升級模型（或把難題交出去）
出現任一訊號就照 playbook/10 §6 升級，不要原地重試：
- 同一個錯誤第二次出現（測試同一處紅、同一個 exception）。
- 自己的解釋前後矛盾（上一輪說 A 是因，這一輪說 A 是果）。
- 開始「改測試遷就實作」而不是修實作。
- diff 越修越大：修一個 bug 動到的檔案數在連續兩輪之間增加。

✅ 正例：sonnet 修 parser 兩輪都紅在同一個 fixture → 停手，把兩輪 diff＋錯誤輸出＋「懷疑是編碼問題」打包升 opus。
❌ 反例：第三輪換個寫法再試一次「說不定這次就過了」——這是擲骰子，不是 debug。

## §2 何時算「真的完成」
全部滿足才可宣稱完成，缺一項就是「進行中」：
1. 驗收指令實際跑過且綠（貼輸出尾段，不是「應該會過」）。
2. fresh-context verifier 驗過（playbook/10 §5）；自己說自己沒問題不算。
3. `git diff` 自查過：每個 hunk 能對應到請求；有對不上的就 revert 該 hunk。
4. 文件同步做了：改了行為/欄位/章節名 → grep 舊名在 README、docs/、src/**/prompts/ 的出現處已一次改完。
5. 完成清單交付給使用者（做了什麼／改了哪些檔／怎麼驗證）。

✅ 正例：「make test 尾段 698 passed；verifier 三條驗收全 PASS；diff 6 hunk 各對應請求第 2 點；docs/11 舊章節名已同步；清單如下」。
❌ 反例：「改好了，邏輯上沒問題」——歷史上「邏輯上沒問題」的文件漂移至少還了三輪債。

## §3 何時該停下來問使用者
**要問**（任一成立）：
- 動作不可逆或難回復：merge 進 main、刪檔、改 docs/ 規劃書本體、動個人持股資料。
- 需求有兩種以上合理解讀，且選錯的代價 > 問一次的成本（列出解讀＋各自 trade-off 再問）。
- 要加新依賴、要改 milestone 範圍、要動 CLAUDE.md 鐵律。
- 發現規劃書（docs/）本身自相矛盾或與現實不符。
- opus 級重試兩輪仍解不了。

**不要問**（自己決定，決定記錄在回報裡）：
- 有慣例可循的實作細節（命名、檔案位置、測試怎麼寫）。
- 查得到的事實（repo 裡有、官方文件有）。
- 預設值合理的參數選擇。

✅ 正例：「00687B 名實不符（實為國泰 20 年美債）——這影響持股標記，兩種處理各有代價，請拍板」。
❌ 反例：「請問測試檔要叫 test_valuation.py 還是 valuation_test.py？」——repo 慣例明擺著，自己看。
❌ 反例（反向）：默默把「+15% 硬擋」放寬成 +20% 因為「感覺太嚴」——門檻值是使用者拍板的，動之前必問。

## §4 方向錯了的訊號（換路，而不是重試）
出現任一訊號，代表該懷疑的是**方法或假設**，不是執行力：
- 連續兩輪都在修「同一個測試」。
- 為了讓測試過而放寬斷言（改期望值、加 tolerance）。
- workaround 上面疊 workaround（第二層 if 特判出現時）。
- 需要動的檔案清單持續膨脹，且說不清為什麼。
- 開始懷疑「是不是資料錯了」卻不去驗證資料。

換路 protocol（照做）：
1. 停手。寫下目前依賴的假設清單（3-5 條）。
2. 挑最底層的假設，用最便宜的方式驗證（讀原始資料、印中間值、跑最小重現）。
3. 假設破了 → 從假設破的那層重新規劃；假設都沒破 → 這是執行問題，照 §1 升級。
4. 回到最後一個已知良好狀態（git stash / checkout），不要在爛泥上繼續蓋。

✅ 正例：M-MH Phase 2 掃不出短窗領先 → 沒有硬調參數硬掃，而是承認「中止條件成立」，砍掉原 Phase 3 設計改窄做——否證也是收穫。
❌ 反例：測試紅 → 把斷言的期望值改成實際輸出讓它綠——這是把 bug 制度化。

## §5 品質底線怎麼驗（分產出型態）
| 產出型態 | 底線驗法 |
|---|---|
| 程式碼 | `make test`（輸出截尾 20 行）綠＋`uv run ruff check src/ tests/` 淨（與 make lint 同範圍）＋mypy 無新增錯＋實跑受影響指令一次 |
| 個股/族群報告 | playbook/60 框架 10 段全有＋空方 ≥ 多方＋抽 3 個數字回查來源檔＋禁用詞 grep（目標價/飆股/強烈建議/絕對/保證；全清單以 playbook/60 禁止事項為準） |
| 研究結論 | 判準在跑實驗**之前**寫定＋量尺與假設同名＋樣本數夠（tiny-N 高 lift 是雜訊，歷史例：6/43）＋對照組或基率有算 |
| 文件改動 | 改名/改章節後 grep 舊名全 repo 出現處為零（排除 docs/08 歷史紀錄與 playbook/_backup） |
| 委派產出 | verifier 逐條驗收全 PASS |

## §6 研究軌專屬判準（本 repo 血淚沉澱）
1. **開工三行**：「本輪唯一要回答的問題」「裁決判準（數字門檻）」「答完即停」。寫不出這三行＝還沒想清楚，不要開跑。
2. **量尺與假設同名**：問起漲機率就用起漲 lift 裁決，問報酬就用報酬分布裁決。（C-P1 教訓：Spearman 測報酬差點誤判否證機率假說，修正後 z=+54 成立。）
3. **前視偏誤**：entry 用次日、未到期樣本排除不補零、下市給 null 不給 0、除息要加回。
4. **NaN 誠實**：缺資料→「未取得」，不填中性值假裝有資料。
5. **大樣本顯著性陷阱**：n 極大時 z 顯著但效應量≈0 是假象（B-P2 教訓：ρ=+0.006、z=2.94「顯著」＝無效應）。裁決看效應量＋方向，z 只當門檻。
6. **否證是合法結局**：預先寫好中止條件，觸發就中止並照實記錄（M-MH Phase 2 前例）。否證的因子記入 memory，防止未來 session 重新發明已死的因子。
7. **模糊題與品味題是 harness 的極限**：拆解、驗證、多樣本評審補得了執行品質，補不了「這個因子在經濟上說不說得通」這類品味判斷。遇到：升級到最強可用模型出第二意見；仍不確定 → 明說「這題超出可驗證範圍」交使用者裁決。不要硬給一個看似自信的答案。
